# 01. What "3DMK" is, and what Venezia should take from it

Research date: 2026-11-04. Track: 3dmk.

## Verdict

**Resolved. 3DMK is real and the spelling was right.** It is [3dmk.com](https://3dmk.com/), titled "3DMK · An agentic development stack, seen at every scale": Nick Olson's personal site, version 2.1.3, last modified 2026-10-31. It documents the one-person agentic harness he built around Claude Code, with an assistant persona called Rei.

It is a **published personal stack, not a product or a framework**. There is nothing to install and no public code. What is available is unusually good documentation of a working method, under CC BY 4.0, including 19 Markdown documents and 2 SQL schema files. Reuse needs credit to "Nick Olson, 3dmk.com".

**The owner has confirmed that 3dmk.com is the site meant, as inspiration only.** Venezia shares no code with it.

## 1. What the stack is

Claude, as Rei, reaches everything through one local MCP gateway. Everything else exists to stop Rei guessing. Olson's framing, from [Getting started](https://3dmk.com/downloads/getting-started.md): most people tell AI *what* to build, whereas this harness is "grounded in governance around how things are done". Its motto is deterministic code, probabilistic creative: trying to force everything into one or the other "leads to sadness".

| System | Job | Worth noting |
|---|---|---|
| **Rei** | Persona loaded by a light CLAUDE.md | Short and direct. Saying "Hi" doubles as a check that init ran and the model works |
| **Core MCP** | Rust tool gateway, 107 tools in 11 groups | Tools load by group, so a session carries only what it needs |
| **Seele** | Documentation graph in PostgreSQL | Three tables. Each node records its token count, so the cost of a read is known first |
| **Scrolls** | Work tracker built for agents | Theme, initiative, epic, story/task/bug, subtask. Replaced his Jira integration |
| **Registry** | Inventory of themes, projects, repos, hosts | An agent gets exact paths without searching the disk |
| **Atlas** | Syntax-tree snapshot per repo per commit | Stored in a separate git repo, so a git diff shows structural change |
| **Magi** | Machine-readable graph of every running part | "Locks" the design. The code is the test |
| **Publishing** | Release route, CLI plus service | A tag is the release. One image runs in dev, then prod |
| **Fetch** | Playwright behind an async API | Screenshots, console messages and page errors for verification |
| **Design** | Review site for HTML artifacts | Device-width frames, element inspector, a vector artboard |
| **Studio** | Agent-run audio workstation | The clearest example of a learning loop (section 4) |
| **NervHQ** | Control-room dashboard | Sessions, queues, code activity, Magi viewer, corpus map |
| **Consul, Vault, Nexus, Postgres, Redis** | Off-the-shelf foundation | Service discovery, secrets, package firewall, state |

Scale, by his account: development began March 2026, and a late-stage chat cites "four months, 294 sessions and 5,935 messages". He reports completing "a full initiative in one overnight session".

## 2. The road from idea to production

This is the core thing to borrow. Sources: [Concept to seed](https://3dmk.com/downloads/concept-to-seed.md), [Orchestration](https://3dmk.com/downloads/orchestration.md).

| Phase | What happens | Artifact | Human gate |
|---|---|---|---|
| Concept | Conversation only. Agent asks what it must do, who uses it, what it must never do | None | `trigger new project` |
| Inventory | Searches for existing documents and shows a table | Table | Confirm |
| Document chain | Fixes one layer per document, each checked against the one before | Overview, Vision\*, Product\*, Technical, Magi, Planning | Each document approved |
| Seeding | Validates, then does a dry run against live data | Initiative, epics, work items | Confirm before anything is created |
| Scope | Sorts items into completed, in progress, ready, blocked | State view | Developer names start and stop |
| Plan | Plan mode: order, parallel groups, model per item, checks per item | Step plan | Approved before any file changes |
| Orchestrate | Main agent routes to subagents and verifies each result | Commits, Scrolls updates | Only when the design must change |
| Epic close | `trigger magi` checks code against the graph | Finding list | Design gaps stop for the developer |
| Dev deploy | Build one image from the tag, verify the running release | Deployment record | None stated |
| Production | Ship the same image, repeat the checks | Deployment record | One approval covers one deploy |

\* Optional: the developer decides per project.

The last step of planning makes a good template. Each work item lands with:

- A type: a **story** for documentation or a **task** for code, "never a mix".
- A short description for lists and dashboards.
- An **agent specification**: file paths, signatures, configuration keys and Technical references.
- Its dependencies.
- An **acceptance-criteria subtask and a testing subtask**, on every task.

Each item must fit one conversation. Foundation epics come first, every epic has one concern, and every epic states exit criteria before work starts. Item size picks the model: small is Haiku, medium is Sonnet, large is Opus.

## 3. How it keeps agents on the rails

These are the mechanisms, ordered by how much I think they matter to Venezia.

1. **"A subagent's report is a claim, not proof."** The orchestrator reruns every check itself before closing an item. Acceptance criteria and tests are separate, because tests can pass on wrong work. His example: tests passed, but the endpoint returned oldest-first when the criteria said newest-first.
2. **Briefs instead of conversation.** A subagent starts from the item's spec, the Technical sections it cites, the Magi nodes it touches, and its checks. It gets no chat history.
3. **Gaps stop the run.** A missing or failing prerequisite makes a trigger stop and name the gap: "a gap means an earlier step was skipped, and the trigger does not fill it with a guess." If Atlas fails, the job stops and does not fall back to reading files by hand.
4. **Guess language is banned from findings.** "Appears to" or "likely" marks a guess, and the job records no guesses. Each finding cites an Atlas line, a Technical section, a standards rule or a Magi ID. Compare Rei's own closing comment: each hard stop "came after I guessed, made up a number, or added a step you never asked for."
5. **Bounds checks against structure.** After each change, Atlas diffs what was added. A class the spec never named is out of bounds, as is an unapproved import, or code doing another node's job. His example caught a leftover parser and a function in the wrong daemon.
6. **Only the human changes the design.** A drift between code and graph has two causes. If the code drifted, it goes back as a fix. If the design missed something, it stops, because "only an approved document changes the design". A refactor moves code back inside the design and never moves the design.
7. **The whole test suite runs after every item.** A failure in an earlier module counts against the new item.
8. **One writer per system.** `core-scrolls-api` is the only reader and writer of its database, with typed operations. Seele's write gate validates a whole batch or rejects it. Registry refuses unsafe changes, such as deactivating a host with active deployments.
9. **Failures never become fixes in place.** A fix lands on main as new work, and a new version takes the whole route.
10. **Releases can only come from tags.** The build starts from an archive of the tag, never the working tree, so an uncommitted file cannot ship. Versions are never reused. Rollback redeploys the previous image.
11. **Guards before deploys.** Deploys hold while users are connected and fail before any change when disk is low. Editing an already-applied database patch fails the deploy.
12. **Resumable by design.** State lives in Scrolls, so each session reads it and starts where the last stopped. Work can pause and move between agents.

## 4. How it learns and documents itself

3DMK has no autonomous self-improvement. Learning is a set of human-rated loops whose output is stored as retrievable nodes. That is less magical than "self-learning" sounds, and it looks far more dependable.

- **Studio is the pattern to copy.** "Reference → session → render → rating → lesson → next render." The human rates each pass, ratings update the session record, and "mistakes become reusable lessons". The design loop has the same shape: research → concept → source artifact → browser render → screenshot review → revision.
- **Research does not bind; approved standards do.** In the Design theme, "research findings can conflict. Only an approved standard binds the work." So agents may accumulate knowledge freely, but only human promotion turns it into a rule.
- **Reconciliation keeps documents true.** Per [Reconciliation](https://3dmk.com/downloads/reconciliation.md), two jobs pull docs and code together. The docs job reads no source and is cheap; config files settle every dispute. The code job compares Atlas with Technical, standards, and Magi in four parallel phases, then scores each Technical section `aligned`, `drift`, `missing` or `contradicted`. Modes are review (writes nothing), reconcile (updates documents) and refactor (updates code). Jobs are idempotent, so a finding on a second run means the first run missed it.
- **Instructions became data.** Triggers began as Markdown and moved into Seele as nodes, with shared steps reused across triggers. He charts context savings of 79% to 97%. He gives no method for those figures, so treat them as directional.
- **Reading has explicit cost and depth.** Edges define what a read loads: `hasPart` loads all descendants, `requires` loads one hop, `references` returns only an ID. Search returns handles, not content. Lists return light fields; details come from a separate read.
- **Every session leaves a record.** A typed close event stores activity, summary, changed repos and token use by model and agent.

## 5. The control surface

I rendered the site in headless Chrome at 1440px and 390px.

- **The system is a place.** Scrolling flies a camera through a three.js city built in Blender. Each system is a building and each repo a tower. Tower shape shows project type, cranes mean recent commits, and moving dots are data in transit. An Explore mode gives free flight through the model, and the footer has a gamepad icon that I did not test.
- **It is drawn as a monochrome technical model:** wireframe towers, callout labels, monospace chapter rail, a "field width" readout that shows the camera's scale. It feels like an architect's study model, and it manages to be striking with almost no colour.
- **Mobile is a real layout.** At 390px the chapter rail collapses to a "17 / 21" counter, and the model sits above a text card.
- **Three depths of the same content.** Each chapter has ELI5, Technical and Commentary versions, switched with one control and addressable at `#chapter/version`.
- **It is friendly to agents.** The site has [llms.txt](https://3dmk.com/llms.txt), Markdown downloads, and page text that needs no scripts. Each download opens with structured front matter.

NervHQ, the working dashboard, is described in text, and I did not see its real interface. As far as the published material shows, the city is a **visualization of the system, not a place to operate it**. The working loop is typing in Claude, plus phone remote control of a workstation session. A search of the home page, `llms.txt` and all downloads found no mention of voice, speech or dictation. The games are things the harness built, not how it is controlled. Those are the openings for Venezia.

## 6. Where 3DMK should not be copied

- **Infrastructure.** Consul, Vault, Nexus, Postgres, Redis, Docker hosts and AWS need a home lab. This machine has no Docker and 8 GB of RAM.
- **Weight.** Six documents and seven human stops suit a platform, but they would kill "try this idea tonight".
- **107 tools.** A tool surface that size took months to grow and has a real context cost.
- **An LLM as orchestrator.** Its orchestrator is itself a model session. BMAD's newer answer is stricter (next section).
- **Evangelion naming.** It is his identity, not ours.

## 7. Runner-up: BMad Method and bmad-loop

Primary sources: [README](https://github.com/bmad-code-org/BMAD-METHOD), [docs](https://docs.bmad-method.org/), [planning path](https://docs.bmad-method.org/plan/choose-a-planning-path/), [bmad-loop](https://github.com/bmad-code-org/bmad-loop). Note that many blog descriptions are out of date: the current README shows stable v6.12 and a v7 preview with a target of mid-November 2026.

**BMad Method** (55,002 stars on 2026-11-04):

- **A delivery loop with variable entry:** Clarify, Plan, Build and verify, Learn and adjust. A vague notion starts at Clarify, a big clear idea at Plan, a small change at Build.
- **One question decides the planning depth: is the intent well defined?** A well-defined intent says what should be true when done, what must not change, and what is out of scope. Well defined goes straight to the Product Owner agent (Sofia); otherwise use research and exploration tools first.
- **Input limits are explicit.** She reads everything in one pass, with a practical ceiling of a few tens of thousands of tokens, so raw piles must be condensed.

**bmad-loop** (177 stars, early open beta, MIT) is the most relevant single idea in this report. Its README says plain Python drives the loop, from picking a story through review, verification and commit, "while LLMs do only the creative work."

- **No LLM in the control loop.** Selection, retries, gates and completion checks are ordinary code.
- **Completion comes from events, never prose.** A session finishes only on a completion event from the agent or the session's death. Timeouts, stalls and budget caps count as failures.
- **Review runs fresh**, without the implementer's context, and is bounded so it cannot oscillate forever.
- **It keeps a board with one writer**, where stories never move backward except through review.
- **Runs resume from on-disk state.** A non-converging story is deferred and the run continues. Critical escalations pause. Work only a human can do parks until confirmed.
- **Deferred work goes to a ledger**, swept later through the same pipeline.
- **Each attempt can run in a git worktree** in a tmux session you can attach to and watch.

## 8. Decisions this implies for Venezia

These are my recommendations, not findings.

| Borrow | From | Venezia form |
|---|---|---|
| Deterministic outer loop | bmad-loop | A plain Node process owns state and spawns `claude -p` sessions. Models never decide "done" |
| Right-sized depth | BMAD | Ask "is intent well defined?", then choose Sketch, Build or Platform. Sketch is a one-page brief and a prototype |
| Compressed document chain | 3DMK | Brief → Spec with an architecture graph → Plan. Default to one file per project |
| Work items as contracts | 3DMK | Spec, dependencies, acceptance and test subtasks, size-based model |
| Verifier apart from builder | Both | Host reruns commands; a fresh-context reviewer checks acceptance |
| Named human gates | Both | Approval cards in the UI, answerable by voice or tap. Publishing always needs one |
| Stop and name the gap | 3DMK | A visible "needs you" state, never a guess |
| Structural diff | 3DMK | Lightweight Atlas: per-commit symbol and import snapshot. Start with TypeScript and Python |
| Knowledge graph with token costs | 3DMK | SQLite with FTS5: nodes, typed edges, versions. No Postgres needed |
| Rated lessons | 3DMK | Rate → lesson → candidate rule → human promotes to standard |
| Reconciliation | 3DMK | Review-only drift job after each initiative, with four scores and idempotence |
| Agent-readable surface | 3DMK | llms.txt, Markdown export and a CLI or API for all UI actions, which covers headless use |
| Layered explanation | 3DMK | Each event at ELI5, Technical and Commentary depth, spoken at the shallowest |
| Place-based interface | 3DMK | Make the world **operable**. Projects as islands in a Venetian lagoon, and work as boats in canals, fits the name; agents, gates and failures become visible things you can act on |
| Release by tag | 3DMK | Build from a clean tag archive, verify, then promote. Target to be chosen by the publishing track |

- Read in full from primary sources: `llms.txt`, full home page text, and these documents: getting-started, concept-to-seed, orchestration, reconciliation, scrolls, seele, core-mcp, nervhq, publishing, design. Partly read: scrolls-schema, seele-schema, registry-schema, registry. Not read: fetch, nexus, postgres, redis, consul-vault, beyond their summaries in llms.txt and on the home page.
- HTTP headers: `last-modified` 2026-10-31. Domain WHOIS: created 2000. GitHub profile through the API.
- Rendering at two widths, and three.js r160 in the import map.
- BMAD README, planning-path page and bmad-loop README, plus star counts through the GitHub API.

**True only as his claims.** I read the documents but ran nothing, and none of this has independent confirmation:

- All 3DMK capability, scale and outcome claims: overnight initiatives, 107 tools, context savings.
- The Trailcast walkthrough is an **illustrative example**, not a recorded project. "Four subagents at once" comes from that example.
- Reliability of bmad-loop. Its own README calls it early beta.

**Secondhand:**

- [arXiv 2606.04967](https://arxiv.org/pdf/2606.04967) comparison of frameworks. I saw it through a search summary only: BMAD deepest process, GSD strongest on context, Spec Kit and OpenSpec most portable. My direct fetch could not read the PDF body.
- Star counts and positioning for other frameworks in search summaries.

**Internal inconsistencies in 3DMK's own material**, which look like snapshot drift:

- Core is 37 projects, 34 projects, or 33 repos, depending on the chapter.
- Registry is 135 repos in 16 themes in chat, and 124 in 15 in the city model.
- The chain has six documents in `llms.txt` and "five" in the reconciliation page.
- The home page says vector search adds semantic retrieval; the Seele page says vector search is deferred.
- Triggers appear both numbered (`trigger 3 new project`) and named (`trigger new project`).
- `llms.txt` calls the model a white card model; my headless render was dark. The site has a theme toggle.
